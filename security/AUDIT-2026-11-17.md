# Doctor Tracker security audit — 2026-11-17

Reviewed baseline: `025df2e`. Findings below describe the original code; line ranges refer to that baseline. Remediations are applied in the working tree and supplied verbatim in [audit-fixes.patch](audit-fixes.patch). The patch contains new utility files and regression tests as well as edits to existing files. No deployment or push was performed.

Result: **2 High, 5 Medium, 3 Low** findings. Nine are remediated locally; the search resource issue is mitigated, with index-backed substring search remaining an architectural follow-up. No Critical issue was identified in this review. This is a code audit, not HIPAA certification or an assessment of cloud account controls.

Use `$API` for an isolated API's `/api` base URL, `$TOKEN` for a staff bearer token, and IDs from test fixtures in all examples. Do not run state-changing PoCs against the shared production database. PoCs describe pre-patch behavior unless stated otherwise.

## 1. High — Activity feeds disclose patients after transfer

**Location:** `server/src/controllers/activityController.js:5–35`; `server/src/controllers/dashboardController.js:20–20,106–106`.

**Vulnerability detail:** Feed authorization uses the historical `Activity.doctors` array. A former doctor continues receiving patient names, status changes, transfer details and reasons from historical events after the patient leaves their current assignment. Direct patient/history routes correctly deny the former doctor, so the feed bypasses that boundary. New events after transfer are generally scoped to the receiving doctor; this finding concerns retained historical events.

**PoC:** Admit a critical patient under doctor A, transfer them to B, then authenticate as A:

```http
GET /api/activity HTTP/1.1
Authorization: Bearer <doctor-A-token>

GET /api/alerts HTTP/1.1
Authorization: Bearer <doctor-A-token>

GET /api/dashboard/stats HTTP/1.1
Authorization: Bearer <doctor-A-token>
```

The original responses can include the transferred patient's name and old clinical events even though `GET /api/patients/<id>` is denied.

**Remediation:** The patch adds `readActivity(req)` to `utils/scope.js`, checks current patient assignment with a database lookup without loading an entire caseload into application memory, and applies that restriction to feeds, unread counts and dashboard activity. It retains staff-directory and transfer-target visibility. Regression tests verify removal from all three responses and denial of direct history access.

## 2. Medium — Doctor IDs expose other caseloads' clinical statistics

**Location:** `server/src/controllers/doctorController.js:94–99,117–139`.

**Vulnerability detail:** Any doctor can enumerate other doctors' patient counts in the directory and clinical status breakdowns in profiles. For small caseloads this can disclose a patient's critical/discharged status. The roster endpoint itself checks ownership, but the aggregate queries do not.

**PoC:** As doctor A:

```http
GET /api/doctors?limit=100 HTTP/1.1
Authorization: Bearer <doctor-A-token>

GET /api/doctors/<doctor-B-id> HTTP/1.1
Authorization: Bearer <doctor-A-token>
```

Observe B's `patientCount` and `statusCounts`.

**Remediation:** Apply `canAccessDoctor` before querying or returning clinical counts. A doctor can still read another doctor's ordinary staff profile to choose a transfer destination; clinical counts and breakdowns are omitted. Admin and nurse visibility remains unchanged. Exact changes are in the `doctorController.js` patch hunks.

## 3. High — Error and request logs can contain PHI

**Location:** `server/src/middleware/errorHandler.js:1–3,23–29`; `server/src/app.js:118–122`; `server/src/utils/activity.js:18–20,37–39`; `server/src/server.js:31–39`; `server/src/config/db.js:14–24`; `server/api/index.js:28–30`; `server/src/scripts/seed.js:263–263`.

**Vulnerability detail:** Production logs print `err.message`; non-production logs print stacks. Mongoose validation/cast/duplicate messages can include rejected patient values and entire documents. Activity failures can include patient names and notes. Fatal and database error handlers also log raw error objects/messages. Path-only HTTP logging removes query strings but still logs attacker-controlled path segments, including unknown routes containing a name or diagnosis. Validation responses concatenate raw database messages.

**PoC:** A request to an unknown path embeds PHI in the old request log:

```http
GET /api/patients/PRIVATE_PATIENT_DIAGNOSIS HTTP/1.1
Authorization: Bearer <staff-token>
```

For the error path, make an audit/database operation fail with a validation/cast error containing a synthetic clinical marker. The old error handler writes that marker to stderr. The regression test injects a synthetic ValidationError and verifies both logs and the response omit the marker.

**Remediation:** Log fixed operation descriptions, never raw exceptions or rejected values. Morgan records registered route templates or `/unmatched`; it never records raw requested URLs. Return a generic validation message and omit response stacks in every environment. The patch updates request, activity, database, serverless and fatal error paths. Patient details intentionally remain in the access-controlled Activity collection, which is itself sensitive data.

## 4. Medium — Clinical changes can succeed without a complete audit trail

**Location:** `server/src/utils/activity.js:6–40`; `server/src/controllers/patientController.js:281–318,328–351,355–438`; `server/src/controllers/doctorController.js:214–239`; `server/src/models/Activity.js:35–40`.

**Vulnerability detail:** Clinical writes occur before audit insertion; audit errors are swallowed. A successful response can therefore represent an unaudited edit or transfer. Generic detail updates do not preserve previous/new values, follow-up entries omit their previous date, and archive/restore/delete entries omit state transitions. Transfer reasons are optional, and an admin can reassign through PUT without a reason.

**PoC:** Temporarily make `Activity.insertMany` reject in an isolated test, then:

```http
PUT /api/patients/<owned-patient-id> HTTP/1.1
Authorization: Bearer <doctor-token>
Content-Type: application/json

{"notes":"Changed despite unavailable audit storage"}
```

Originally this returns success and persists the note. Also, `POST /api/patients/<id>/transfer` with only `{"doctor":"<target-id>"}` succeeds without a reason.

**Remediation:** New `utils/auditedMutation.js` uses MongoDB transactions with Mongoose session propagation; successful responses are sent only after commit. Every patient mutation, roster admission/archive and whole-caseload transfer uses the wrapper. Audit failures propagate and abort the transaction. Detail edits record `changes[{field,from,to}]`; follow-ups and lifecycle events record before/after states. Transfers require a sanitized nonempty reason; PUT directs reassignment to the transfer endpoint. Database work inside these write transactions is sequential where necessary. Exact code is included in the patch, including the new wrapper and schema field.

**Deployment requirement:** Transactions require a replica set or supported sharded cluster; MongoDB Atlas supports this topology. A standalone local `mongod` must be configured as a replica set. Historical missing audit entries cannot be reconstructed by this patch. Regression tests confirm both rollback on audit failure and successful actor/timestamp/before/after recording.

## 5. Medium — Rate limits reset across serverless instances

**Location:** `server/src/app.js:75–101`; `server/api/index.js:1–3`.

**Vulnerability detail:** Both limiters use express-rate-limit's default process-local memory store. Vercel instances have independent counters and lose them on recycling. The configured 25 authentication attempts and API limits are therefore not deployment-wide limits. See the [express-rate-limit store documentation](https://github.com/express-rate-limit/express-rate-limit/blob/main/docs/reference/stores.mdx).

**PoC:** In an isolated environment, start two API processes with the same database/secret and distribute more than 25 invalid login attempts between them. Neither original process reaches its own 25-request threshold. Recycling a process also resets its count. This is a topology reproduction, not a load attack executed against production.

**Remediation:** The new `MongoRateLimitStore` shares atomic counters in MongoDB, with namespace separation and a TTL index. Production uses it for both limiters; development/test defaults retain memory stores. Staff limits remain keyed by an HS256-verified JWT subject; unauthenticated and invalid-token requests use normalized IPs. Store errors fail closed through Express error handling. A regression test verifies ten concurrent increments across independent store instances produce exactly counts 1–10.

**Operational detail:** The database principal needs permission to create the `rate_limits` collection/index and read/write its counters. The TTL index removes expired counter records asynchronously. Windows are fixed wall-clock intervals; a boundary may allow two adjacent windows' quota in a short interval.

## 6. Medium — Direct API deployments trust spoofed forwarded IPs

**Location:** `server/src/app.js:21–22`.

**Vulnerability detail:** Unconditional `trust proxy = 1` trusts a client-supplied `X-Forwarded-For` when the standalone Node server is directly reachable. Attackers can rotate this header to change anonymous/login rate-limit buckets. This finding depends on deployment topology; a correctly configured platform proxy that overwrites forwarded headers prevents this particular direct-access exploit.

**PoC:** Against a directly exposed standalone test server, repeat login attempts while varying:

```http
X-Forwarded-For: 198.51.100.10
```

Then use `.11`, `.12`, etc. The original configuration treats these values as client IPs.

**Remediation:** The patch defaults standalone deployments to no proxy trust, selects one trusted hop on Vercel, and allows explicit `TRUST_PROXY_HOPS` for known reverse-proxy topologies. If configured behind a proxy, prevent direct access and ensure all paths have the expected trusted hop count. For a directly reachable process use `TRUST_PROXY_HOPS=0`.

## 7. Medium — Pagination does not bound database search work

**Location:** `server/src/controllers/patientController.js:30–39,157–178,187–190`; `server/src/controllers/doctorController.js:68–71,90–94,251–269`; `server/src/controllers/dashboardController.js:40–106`.

**Vulnerability detail:** Search regexes are escaped and bounded, preventing regex injection, but unanchored case-insensitive substring searches and counts may inspect many records. A page size of 100 bounds returned rows, not records examined or sort/count work. Dashboard aggregations also lacked execution deadlines. [MongoDB documents the indexing limitations of case-insensitive regex queries](https://www.mongodb.com/docs/manual/core/index-case-insensitive/).

**PoC:** On a large isolated fixture dataset:

```http
GET /api/patients?search=unlikely-substring&page=10000&limit=100 HTTP/1.1
Authorization: Bearer <staff-token>
```

Compare `explain('executionStats')` for the equivalent scoped query; document examinations can substantially exceed returned rows. No production-scale load test was performed.

**Remediation applied:** `mongoose.set('maxTimeMS', 2000)` bounds supported queries and aggregates. Existing field whitelists, 100-character escaped search terms, page caps, scopes and export row caps remain in force. Email validation is now bounded to 254 input characters as additional regex-work hardening.

**Residual limitation:** This is a resource-budget mitigation, not an index-backed substring-search implementation. Atlas Search or a deliberate change to indexed prefix/token semantics, plus cursor pagination for deep pages, is required for large deployments. Actual deployed index utilization was not measured; no production index migration was executed.

## 8. Low — Payload limit exceeds specification; early responses miss no-store

**Location:** `server/src/app.js:102–116`.

**Vulnerability detail:** JSON and URL-encoded parsers accept 1 MB, rather than the requested 10 KB. Cache-prevention middleware runs after parsers and limiters, so parser/rate-limit errors bypass it. A 1 MB allowance alone is not proof of a denial-of-service exploit, but it enlarges the documented processing budget unnecessarily.

**PoC:** Send JSON with an 11,000-character string to `/api/auth/login`; the original parser accepts its size, while the required policy should return 413. A body exceeding 1 MB returns 413 without the original no-store middleware running.

**Remediation:** Set both parsers to `10kb`, use the simple URL-encoded parser, and install `/api` no-store headers before CORS, limiters and parsers. The serverless adapter also sets no-store before its configuration/database error paths. The boundary regression verifies 413, no-store and frame denial.

## 9. Low — Production CORS implicitly allows localhost

**Location:** `server/src/app.js:37–42`.

**Vulnerability detail:** The production allowlist always includes both localhost frontend origins. This expands browser access beyond configured production origins. CORS does not grant bearer tokens and this is not an independent authentication bypass.

**PoC:** Against a production-mode test process with a non-local `CLIENT_URL`, send `Origin: http://localhost:3000`. The original response grants that origin.

**Remediation:** Add implicit local origins only outside production. Production accepts configured `CLIENT_URL` origins and requests without Origin; the latter remain subject to authentication. A fresh-process production regression confirms localhost is denied and the configured staff origin is allowed.

## 10. Low — CSV guard omits line-feed and whitespace-obscured prefixes

**Location:** `server/src/utils/csv.js:5–9`.

**Vulnerability detail:** Direct `=`, `+`, `-`, `@`, tab and CR prefixes are already guarded. LF and whitespace-before-formula variants are not. Spreadsheet/importer normalization differs, so exploitability depends on how the exported file is imported. This is CSV defense hardening; no spreadsheet execution was demonstrated.

**PoC:** With an isolated database fixture or an existing legacy record whose exported value is `"\n=1+1"` or `"  =1+1"`, export `/api/patients/export`. The old CSV helper does not prefix an apostrophe. Current patient text writes trim leading whitespace, reducing this path for newly entered names/conditions, but the reusable exporter also handles stored/legacy values. See [OWASP's CSV injection testing guidance](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/07-Injection/21-CSV_Injection).

**Remediation:** The exact patched guard is:

```js
if (/^(?:[\t\r\n]|\s*[=+\-@])/u.test(s)) s = `'${s}`;
```

RFC-style delimiter/quote/newline escaping remains in place. Regression tests cover every specified execution prefix plus LF and whitespace-obscured formulas. Spreadsheet-specific import/re-save behavior remains outside this test suite.

## Additional transport hardening applied

The API previously used Helmet's default `SAMEORIGIN` frame policy and disabled its CSP. The patch sets `X-Frame-Options: DENY` and an API CSP with `default-src 'none'` and `frame-ancestors 'none'`. Cross-origin API consumption remains allowed through CORS. Next.js already sets frame DENY, nosniff, COOP same-origin, restricted connect-src, referrer/permissions policy and production HSTS; it was not modified.

## Verification and practical limits

- Full backend integration suite: **49/49 passing** after patches, against the pre-existing isolated test database names. Regression cases cover former-doctor feeds, foreign clinical counts, audit rollback, audit change values/actor/timestamps, shared atomic counters, payload/header boundary, production-startup CORS, CSV prefixes and PHI-free errors.
- Server and client ESLint: pass. `git diff --check`: pass.
- Existing browser suite was **not rerun**. Its hardcoded local services normally connect to the same Atlas database as production and it writes/deletes fixtures. Frontend source was not changed. No browser/build result from an earlier handoff is claimed as a new result.
- No seed, production data change, live exploit attempt, cloud-setting change, credential rotation, index synchronization, commit or push was performed. Test execution created/dropped only the existing dedicated test databases.
- Existing documented tradeoffs remain: localStorage JWTs; client-only logout until JWT expiry; inline scripts in the frontend CSP. These increase impact if a future script-injection path appears. The intentionally public demo credentials remain appropriate only for the documented synthetic demo; this audit did not authorize or perform account replacement.
- Shared rate counters add database operations per API request and fail closed if their database storage fails. Two-second query deadlines can reject expensive legitimate queries; tune against measured workloads rather than silently removing the budget.

The exact production code and regression-test patch is [audit-fixes.patch](audit-fixes.patch). It targets the reviewed baseline and is already applied to this workspace; do not apply it a second time here.
